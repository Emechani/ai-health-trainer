# 개인 데이터·백업·복구 기준

## 보관 대상을 구분합니다

| 대상 | 처리 |
|---|---|
| Python/HTML 소스·Migration·의존성 파일·문서 | Git 등 코드 저장소 |
| SQLite DB와 업로드 media/ | 개인 데이터 백업. 공개 저장소에 넣지 않음 |
| 루트 meal_images/ 등 예전 업로드 폴더 | 기존 파일이 있으면 삭제하지 말고 별도 보존. 현재 MEDIA_ROOT와 실제 DB 경로를 확인해 이관 |
| .env·Django 운영 비밀 키·Google OAuth JSON | 별도 암호화 비밀 저장소. 데이터 백업 압축 파일에 섞지 않음 |
| .google_tokens 및 token*.json | 기본 데이터 백업·소스 배포에서 제외. 새 환경에서는 재인증 권장 |
| staticfiles/ | collectstatic으로 재생성. 원본 소스 유지 |
| AI 캐시·venv·__pycache__ | 백업 제외. 재생성 |

개인 DB에는 계정·체중·식사·대화 등 민감한 정보가 들어 있습니다. 업로드 사진도 개인 데이터입니다. 백업은 디스크 암호화/암호화 저장소와 제한된 서비스 계정 권한을 사용하세요. Windows 폴더의 ACL과 BitLocker, 원격 저장소의 접근 권한도 별도로 설정합니다. 백업 도구가 자체적으로 암호화를 제공하지는 않습니다.

## 백업 실행 예시

이번 작업에서는 실제 사용자 데이터를 복사하거나 외부에 전송하지 않았습니다. 아래는 관리자가 직접 실행할 절차입니다.

1. 신규 식사·운동·체중 입력과 파일 업로드를 잠시 중지합니다. DB와 사진을 동일 시점으로 맞추려면 애플리케이션·예약 작업의 쓰기를 모두 멈추세요.
2. 실제 DB와 MEDIA_ROOT 경로를 확인합니다. 소스 밖의 암호화된 백업 드라이브/폴더를 준비합니다.
3. 다음 명령에서 **실제 경로로 교체**해 실행합니다.

```powershell
.\venv\Scripts\python.exe scripts\backup_data.py --database C:\HealthData\db.sqlite3 --media-root C:\HealthData\media --output D:\PrivateHealthBackups
```

도구는 SQLite backup API로 DB 복사본을 만들고 무결성을 검사한 뒤 media 파일을 복사합니다. 새 날짜별 폴더에 저장하며 기존 백업을 덮어쓰거나 삭제하지 않습니다. media의 심볼릭 링크·접합점은 거부해 다른 위치의 파일을 따라 복사하지 않습니다. 목적지는 프로젝트·media 폴더 밖이어야 합니다.

DB 복사본, media/, 파일별 SHA-256·크기를 기록한 manifest.json이 생성됩니다. 명령 실행 중 오류가 나면 부분 백업이 남을 수 있습니다. manifest.json이 정상 생성된 백업만 사용하고, 새 백업을 검증하기 전에 마지막 정상 백업을 삭제하지 않습니다.

4. 생성된 DB 무결성·manifest의 파일 해시와 사진을 확인합니다. 성공 확인 후 쓰기를 재개합니다.

실행 중인 DB 파일만 단순 Copy-Item 하거나, SQLite의 WAL/SHM 파일을 무시한 파일 복사로 일관성이 보장된다고 가정하지 마세요. DB backup API를 사용해도 업로드와 DB 사이의 동시성까지 맞추는 것은 아니므로 위 쓰기 중지 절차가 필요합니다.

## 보관 기준

- 매일 1회 + Migration/업데이트/데이터 이전 직전 백업
- 일간 7개·주간 4개·월간 3개를 기본 보관안으로 검토
- 다른 장치/위치에 암호화 사본 1개 이상. 동일 디스크의 백업만으로 장애 복구를 준비했다고 판단하지 않음
- 보관 기간이 지나도 새 백업의 복구 확인 전 마지막 정상 백업을 삭제하지 않음
- 운영 비밀 키는 데이터 복구와 별도로 안전하게 보관. 기존 서명 데이터·세션 유지에 필요할 수 있으며, 유출 시에는 복구보다 키 회전·재인증을 우선 검토
- 토큰 사본이 꼭 필요하다면 별도 암호화·최소 접근 권한·만료/철회 정책 아래에서 관리자가 직접 처리. 이 도구는 토큰을 읽거나 복사하지 않음

## 복구 리허설 (기존 데이터 덮어쓰기 금지)

1. 별도 PC 또는 비어 있는 새 데이터 폴더를 준비합니다. 예: `C:\HealthRestoreTest`. 운영 폴더를 대상으로 하지 않습니다.
2. 같은 코드 버전과 의존성으로 가상환경을 만들고 환경 파일은 별도로 설정합니다.
3. 백업의 manifest 해시·DB 무결성을 확인합니다.
4. `database.sqlite3`와 media/를 새 폴더에 복사하고 테스트 환경의 `DJANGO_DB_PATH`, `DJANGO_MEDIA_ROOT`를 이 경로로 지정합니다.
5. 외부 API와 메일 발송을 끈 환경에서 날짜별 기록·사용자 구분·사진·식단 보관함을 확인합니다. 복구본을 외부 공개하지 않습니다.
6. `manage.py migrate --plan`으로 코드와 DB의 Migration을 비교합니다. 실제 적용 전 복구본도 다시 백업합니다.
7. 운영 복구는 서비스 쓰기를 멈추고 현재 상태를 별도 보존한 뒤, 검증한 새 데이터 경로로 설정을 전환하는 방식으로 진행합니다. 운영 DB를 먼저 삭제하거나 초기화하지 않습니다.

백업 스크립트의 가상 데이터 검증은 실제 운영 백업·복구 리허설을 대신하지 않습니다.
